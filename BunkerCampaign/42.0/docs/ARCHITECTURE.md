# Архитектура технического прототипа

## Границы этапа

Этот пакет реализует инфраструктуру серверного состояния, вентиляцию и нормализованное состояние водяного контура. Это ещё не полный MVP кампании. Исследования, навыки, транспорт, события Director и GM-панель пока отсутствуют; заражение персонажей и защитная экипировка реализованы отдельным Toxic MP-форком.

Целевая среда — локально установленный Project Zomboid Build 42.19. Папка `42.0` — формат варианта мода для ветки Build 42; `versionMin=42.19` в `mod.info` запрещает запуск на более старой версии.

## Разделение ответственности

```text
Клиентское окно
      |
      | requestState / setVentilation(enabled)
      v
ServerCommands -- проверка команды и роли admin
      |
      v
CampaignState -- единственная точка изменения состояния
      |
      +--> VentilationSimulation -- чистая расчётная логика
      |
      +<-- Integration/WaterpipesAdapter -- доверенный серверный снимок воды
      |
      +--> ModData -- сохранение вместе с миром
      |
      +--> stateSnapshot -- всем клиентам или конкретному клиенту
```

Клиент никогда не передаёт серверу `condition`, `filterRemaining`, `co2`, загрязнение, статус или ревизию. Для переключения передаётся ровно одно логическое значение `enabled`; сервер проверяет тип и административную роль отправителя.

## Состояние

Сервер хранит таблицу под ключом `BunkerCampaign.State` через `ModData.getOrCreate`. Игра сохраняет Global ModData вместе с миром. Клиентам эта таблица напрямую не выдаётся: `CampaignState.snapshot()` строит отдельный ограниченный снимок.

Основная часть схемы:

```lua
{
    version = 2,
    campaignId = "default",
    revision = 0,
    bunker = {
        modules = {
            ventilation = {
                enabled = true,
                condition = 1.0,
                status = "operational",
                filterRemaining = 1.0,
                co2 = 400,
                externalContamination = 0.0,
                internalContamination = 0.0,
                recirculationUnlocked = false
            },
            water = {
                adapterOnline = false,
                pumpActive = false,
                pumpCondition = 0.0,
                status = "offline",
                filterRemaining = 0.0,
                stored = 0.0,
                capacity = 0.0,
                contamination = 0.0,
                flowPerMinute = 0.0,
                powerDemandKw = 0.0,
                source = "none"
            }
        }
    },
    auditLog = {}
}
```

`internalContamination` добавлено сверх минимальной схемы ТЗ, потому что требование о проникновении наружного загрязнения при пустом фильтре иначе негде хранить.

## Версионирование и миграции

`StateSchema.prepare` выполняется только на сервере во время `OnInitGlobalModData`.

- отсутствующая версия считается версией 0;
- миграция 0 -> 1 добавляет недостающие таблицы и поля без замены уже существующей таблицы `ModData`;
- миграция 1 -> 2 добавляет модуль воды, сохраняя вентиляцию и журнал существующего мира;
- числовые значения проверяются на тип, NaN, бесконечность и допустимый диапазон;
- неизвестная более новая версия останавливает загрузку с явной ошибкой, чтобы старый код не повредил сохранение;
- миграции записываются в журнал.

## Симуляция вентиляции

Расчёт вызывается событием `EveryOneMinute`, а не каждый кадр.

- включённая исправная вентиляция снижает CO2 до нижней границы 400 ppm;
- выключенная или отказавшая вентиляция повышает CO2;
- фильтр расходуется только при включённой исправной вентиляции;
- наружное загрязнение умножает расход фильтра;
- после исчерпания фильтра наружное загрязнение повышает внутреннее;
- статус выводится из исправности, CO2, ресурса фильтра и внутреннего загрязнения.

Полный снимок отправляется раз в пять игровых минут, при административном переключении и по запросу подключившегося клиента. Это ограничивает сетевой трафик и оставляет интерфейс достаточно свежим.

## Журнал

Серверный журнал хранится в состоянии кампании и ограничен 100 записями. Записываются:

- создание и миграции состояния;
- ручное включение/выключение вентиляции;
- переходы между состояниями модуля;
- исчерпание фильтра;
- отклонённые или неизвестные клиентские команды.

Клиент получает только последние 12 записей, окно отображает последние две.

## Использование существующих модов

Исходные папки игры и Workshop используются только для чтения. Для этого этапа изучены:

- The Ark — локальный MP-форк строит бункер и сохраняет совместимую схему Global ModData;
- Toxic Zones STALKER B42 — локальный MP-форк отвечает за зоны, экспозицию и фильтры;
- Bandits 42.x и Waterpipes 42.x — реальные обработчики `OnClientCommand`;
- Cryogenic Winter — кандидат на слой экстремального холода в survival-этапе.

Ядро по-прежнему может запускаться отдельно. `BunkerCampaignIntegration` связывает его с MP-форками и Waterpipes, регистрирует фиксированную линию бункерного насоса на сервере и переводит внутренние единицы Waterpipes в литры. Следующий этап — серверная дезактивация, использующая воду и расходники.
